# 3선 자동매매 (three-line-trader)

관심종목의 실시간 시세를 감시하고, 종목별 상태 머신에 따라 자동으로 매수 · 부분 익절 · 청산을 수행하는 국내주식 자동매매 프로그램.

| 구성 | 사용 기술 |
|---|---|
| 증권사 연동 | 키움증권 **REST API + WebSocket** (모의/실전 전환 지원) |
| 저장소 | **SQLite** — 상태 영속화, 장애 복구, 매매 이력 |
| 화면 | **Tkinter** (표준 라이브러리) |
| 알림·원격 조회 | **Discord 봇** — 실시간 알림, 슬래시 명령, 장중 대시보드 |
| 패키지 관리 | **uv** (Python 3.13) |
| 복기 차트 | **matplotlib** — 일봉·3분봉 PNG 생성, Discord 전송 (미리보기 확대·축소는 **Pillow**) |

## 1. 빠른 시작

```bash
uv sync                               # 의존성 설치
cp config.toml.example config.toml    # 키움 앱키 · Discord 봇 토큰 입력
uv run simulate.py                    # 연습 모드 (가짜 틱, 실제 주문 없음)
uv run main.py                        # 실전 모드
```

**설정 파일** — `config.toml` 에 모의/실전 앱키와 Discord 봇 정보를 넣는다.

```toml
[kiwoom.mock]
appkey = "모의투자 앱키"
secretkey = "모의투자 시크릿키"
account = "0000-0000 위탁종합"   # 화면 표시용 (선택)

[kiwoom.real]
appkey = ""
secretkey = ""
account = ""

[discord]                     # 봇 하나로 알림·명령·대시보드를 모두 처리한다
bot_token = "봇 토큰"
channel_id = "채널 ID"
allowed_users = ["본인 사용자 ID"]

[fees]                        # 세후 실현손익 계산용 (아래 "거래비용 설정" 참고)
commission_rate = 0.00015
tax_rate = 0.0015

[schedule]                    # 무인 운용 (아래 "자동 스케줄" 참고)
enabled = false
start = "08:55"
stop = "15:30"
summary = "15:35"             # 일일 요약 — 자동화는 여기서 끝난다

[chart]                       # 복기 차트 (아래 8장 참고)
font = ""                     # 비우면 맑은 고딕 → 나눔고딕 순 자동 선택
```

**거래비용 설정** — 세후 손익을 정확히 보려면 실제 요율을 넣어야 한다.
수수료율은 계좌마다 다르므로 영웅문의 수수료 안내에서, 거래세율은 제도 변경이 잦으므로
거래내역의 실제 차감액으로 확인해 맞춘다. 적용 중인 요율은 프로그램 시작 로그에 표시된다.

> **보안**: 앱키·시크릿이 유출되면 타인이 내 계좌로 주문을 낼 수 있다. `config.toml` 은 절대 커밋하지 않는다 (`.gitignore` 등록됨). 커밋 대상은 `config.toml.example` 뿐이다.

**첫 연결 점검** — 실제 주문 없이 토큰·조회·WebSocket 을 확인한다.

```bash
uv run check_kiwoom.py                 # 모의투자 점검 (토큰 → REST 조회 → WS 수신)
uv run check_kiwoom.py --real          # 실전 계좌로 점검
uv run check_kiwoom.py 005930 --buy1   # 모의투자 한정: 1주 매수 → 체결통보까지 실측 (장중)
```

## 2. 전략 개요

관심종목에 편입된 각 종목은 사용자가 직접 설정한 **3개의 기준선**을 가진다.

```
현재가 > 1선 > 2선 > 3선
```

- **1선 이탈** 시 1차 매수, **2선 이탈** 시 2차 매수(물타기, 평단 재계산), **3선 이탈** 시 전량 손절
- 상승 시 평단가 대비 **+3% → +5% → +7%** 에서 단계적으로 부분 익절
- 익절 시작 이후에는 추가 매수 없음. 익절 진행 중 **평단가(본절) 이탈 시 잔량 전량 청산**

### 자금 관리와 설정값

**총 운용금액 ÷ 최대 보유 종목 수 = 종목당 배분 금액**이며, 1·2차 매수 금액은 배분 금액의 절반씩 자동으로 채워진다(직접 수정 가능). 자동 채움과 배분 계산은 모두 **버림(floor)** 이라 1차 + 2차 합계가 종목당 배분을 넘는 일이 없다.

매수 수량은 **트리거 시점의 체결가로 `floor(금액 ÷ 가격)`** 을 즉석 계산한다. 매수는 항상 기준선 이하에서 발동하므로 "매수 금액 ≥ 기준선"이면 최소 1주가 보장된다(등록 시 검증).

| 항목 | 설명 | 기본값 |
|---|---|---|
| 1선 / 2선 / 3선 | 종목마다 개별 설정 (1선 > 2선 > 3선) | 필수 입력 |
| 총 운용금액 / 최대 종목 수 | 전역 설정. 종목당 배분 금액의 기준 | 10,000,000원 / 10종목 |
| 1차 / 2차 매수 금액 | 전역 설정. 적용 시 '대기' 종목에 즉시 반영, **보유 중 종목은 진입 시점 값 유지** | 종목당 배분의 50% / 50% |
| 익절 트리거 % | 전역 설정 — 평단가 대비 1 / 2 / 3차 익절 기준 | 3% / 5% / 7% |
| 익절 비중 | 전역 설정 — **최초 보유 물량** 기준 매도 비율 (합계 100%) | 40% / 50% / 10% |

**익절 수량 계산** — `i차 매도량 = floor(총량 × 누적비중) − 기매도량`, 마지막 차수는 잔량 전부. 버림 누적이라 총량이 정확히 일치하고 초과 매도가 구조적으로 불가능하다. 다만 보유량이 적으면 앞 차수가 0주가 되어 뒤로 밀린다(예: 40/50/10% 기준 2주 보유 → 0 / 1 / 1주). 이런 소량 종목은 우클릭 **수동 전량 청산**으로 직접 정리하는 것을 권장한다.

## 3. 상태 머신

총 **8개 상태**로 구성된다.

```
대기, 1차 매수, 1차 매수 + 3% 익절, 1차 매수 + 5% 익절,
2차 매수, 2차 매수 + 3% 익절, 2차 매수 + 5% 익절, 종료
```

```mermaid
stateDiagram-v2
    대기 --> 1차매수 : 현재가 ≤ 1선
    1차매수 --> 1차3익절 : ≥ 평단 +3% (40% 매도)
    1차매수 --> 2차매수 : ≤ 2선 (추가매수, 평단 재계산)
    1차3익절 --> 1차5익절 : ≥ 평단 +5% (50% 매도)
    1차3익절 --> 종료 : ≤ 본절 (전량 청산)
    1차5익절 --> 종료 : ≥ 평단 +7% 또는 ≤ 본절 (전량 청산)
    2차매수 --> 2차3익절 : ≥ 새평단 +3% (40% 매도)
    2차매수 --> 종료 : ≤ 3선 (전량 손절)
    2차3익절 --> 2차5익절 : ≥ 새평단 +5% (50% 매도)
    2차3익절 --> 종료 : ≤ 본절 (전량 청산)
    2차5익절 --> 종료 : ≥ 새평단 +7% 또는 ≤ 본절 (전량 청산)
```

### 상태 전이 규칙

| 현재 상태 | 조건 | 다음 상태 | 액션 |
|---|---|---|---|
| 대기 | 현재가 ≤ 1선 | 1차 매수 | 1차 매수 (평단 = 체결가) |
| 대기 | 현재가 ≤ 2선 (갭) | 2차 매수 | 1·2차 수량을 **한 주문으로 동시 매수** |
| 대기 | 현재가 ≤ 3선 (갭) | 종료 | **주문 없음.** 진입 금지, 당일 매매하지 않음 |
| 1차 매수 | ≥ 평단 × 1.03 | 1차 + 3% 익절 | 최초 물량의 40% 매도 |
| 1차 매수 | ≤ 2선 | 2차 매수 | 추가 매수, 평단가 재계산 |
| 1차 + 3% | ≥ 평단 × 1.05 | 1차 + 5% 익절 | 최초 물량의 50% 매도 |
| 1차 + 3% | ≤ 평단 (본절) | 종료 | 잔량 전량 청산 |
| 1차 + 5% | ≥ 평단 × 1.07 | 종료 | 잔량 전량 청산 |
| 1차 + 5% | ≤ 평단 (본절) | 종료 | 잔량 전량 청산 |
| 2차 매수 | ≥ 새 평단 × 1.03 | 2차 + 3% 익절 | 최초 물량의 40% 매도 |
| 2차 매수 | ≤ 3선 | 종료 | 전량 청산 (손절) |
| 2차 + 3% | ≥ 새 평단 × 1.05 | 2차 + 5% 익절 | 최초 물량의 50% 매도 |
| 2차 + 3% | ≤ 새 평단 (본절) | 종료 | 잔량 전량 청산 |
| 2차 + 5% | ≥ 새 평단 × 1.07 | 종료 | 잔량 전량 청산 |
| 2차 + 5% | ≤ 새 평단 (본절) | 종료 | 잔량 전량 청산 |

### 설계 원칙

- 익절 % 와 본절 기준은 **항상 그 시점의 평단가 기준**. 2차 매수 후에는 낮아진 새 평단가로 전부 재설정된다. 매도(익절)는 평단가를 바꾸지 않는다.
- 익절 비중은 **최초 보유 물량 기준**. 2차 매수 경로에서 최초 물량 = 1차 + 2차 매수 합산 총량.
- **익절 시작 후 추가 매수 없음.** 평단 > 2선이 구조적으로 보장되므로, 익절 상태에서 하락하면 2선 도달 전에 본절 청산이 먼저 발동한다.
- 일반적인 하락 흐름: `1차 매수 → 2차 매수 → 3선 손절`

## 4. 운영 규칙

| 규칙 | 내용 |
|---|---|
| 판정 가격 | **WebSocket 실시간 체결가(0B)** 기준. 모든 가격 조건은 **터치 시 발동** (하락 ≤, 상승 ≥) |
| 주문 방식 | 조건 충족 → 시장가 주문 → **체결통보(00) 수신 후** 평단·잔량 갱신 및 상태 전이 확정. 평단은 지시 가격이 아닌 **실제 체결가** |
| 갭 / 동시 조건 | 한 틱(특히 시가)이 여러 단계를 통과하면 중간 단계 생략. 상승 갭은 누적 비중을 한 주문으로 매도하고 +7% 이상이면 즉시 전량 청산. 하락 갭은 '1차 매수'에서 3선 이하 직행 시 2차 매수 생략하고 전량 손절 |
| 최대 종목 수 | 1차 진입 시점에 보유 종목이 최대치면 **주문 없이 '대기'로 보류**한다. 청산으로 슬롯이 비면 같은 규칙(1선~2선이면 1차, 2선~3선이면 1·2차 동시)으로 다시 진입한다. 보류 중에는 **종목 행 상태에 "(보류)" 가 표시**되고, 로그는 사유나 가격 구간(1선~2선 / 2선~3선)이 바뀔 때만 남는다(틱마다 남기면 하루 수백 건이 된다 — 실측 107건). 알림은 종목당 1회 |
| 주문 수량 | `floor(금액 ÷ (트리거 가격 × (1 + 수수료율)))`. 매수 수수료를 빼먹으면 배분 금액을 꽉 채운 수량이 나와 증권사 여력을 1주 차이로 넘어선다. 예수금 검사도 **조회값의 98%까지만** 사용한다 — 직전 체결이 증권사 여력에 반영되기까지 시차가 있어, 꽉 채워 주문하면 "매수증거금이 부족합니다" 로 거부된다(2026-07-29 실측). 계산 결과가 **0주면 주문을 보내지 않고 '보류'** 로 둔다 — 거부된 주문 3회가 쌓이면 당일 그 종목 주문이 통째로 막히기 때문이다. 가격이 더 내려가면 1주가 되므로 대기 상태로 남긴다 |
| 예수금 부족 | 코어가 매수 실행 전 주문가능금액을 확인한다(상태 머신은 관여하지 않음). **1차·2차 모두 '보류'** — 종료시키지 않고 대기 상태로 두어 자금이 회수되면 다시 진입한다(2차 보류 중에도 1차 물량의 손절·익절은 계속 동작). 조회는 짧게 캐시하고 **체결이 나면 캐시를 즉시 버려** 회수 자금을 바로 인식한다 |
| 최소 진입 수량 | 1차 매수 예상 수량이 **3주 미만이면 경고**한다(등록·편집 시, 전역 설정 적용 시, 실제 진입 시). 진입을 막지는 않으며, 소량 종목은 수동 전량 청산으로 정리하면 된다 |
| 재진입 | 한 종목은 **하루 1회만 진입**. '종료' 상태는 당일 유지. 우클릭 `종료 → 대기 초기화` 로 당일 재시작 가능 |
| 매매일별 리스트 | 관심종목·포지션은 **(매매일, 종목코드)** 단위로 저장되어 날짜별로 독립. 저녁에 다음날 날짜로 이동해 등록하고, 다음날 그 날짜에서 감시를 시작한다. 과거 날짜로 이동하면 그날의 최종 상태·실현손익을 조회할 수 있다 |
| 오버나이트 | 보유 중인 종목은 우클릭 **다음 매매일로 이월**로 상태·평단·잔량을 그대로 넘긴다(주말 자동 건너뜀). 등록 시 시작 상태를 직접 지정할 수도 있다 |
| 감시 중 변경 차단 | 감시 중에는 등록·편집·삭제·CSV 불러오기·설정 적용·모드/매매일 전환이 모두 차단되고 해당 위젯이 비활성화된다(UI 경고 + 코어 거부 이중 방어). **주문가능금액 새로고침·알림 수준 변경·수동 청산·로그 조작은 허용** |
| 수동 개입 | 종목 우클릭 메뉴: **다음 매매일로 이월(상태·평단·수량)** · **다음 매매일로 이월(전체)** · 수동 전량 청산(시장가) · 종료 → 대기 초기화 · 차트 보기 · 편집 · 관심종목 제외. **Ctrl·Shift 로 여러 종목을 골라 한 번에** 처리할 수 있고, 한 종목씩 다뤄야 하는 항목(수동 청산·리셋·편집)은 다중 선택 시 비활성화된다 |

| 체결 오차 기록 | 주문을 유발한 **판정가**와 **실제 체결가**를 함께 남긴다. 시장가 주문은 트리거 가격에 그대로 체결되지 않으므로(실측 -1.9% ~ +0.2%), 쌓인 데이터로 "평균 오차·최악값·손익 영향"을 집계해 나중에 주문 방식(지정가 혼합·분할 주문)을 재검토할 근거로 쓴다. **판정·주문 로직에는 전혀 관여하지 않는 기록 전용 값이다** |
| 최고/최저가 (MFE/MAE) | 보유 구간 동안의 최고가·최저가를 기록한다. "손절된 종목이 그전에 얼마까지 올랐나", "수익 종목이 얼마나 밀렸다 왔나" 를 나중에 집계해 익절률·비중·3선 간격을 조정하는 근거로 쓴다. 틱으로 갱신한 값을 **1분마다 DB 에 옮긴다** — 전이 때만 옮기면 매수 후 청산 없이 보유만 한 날은 체결가에 멈춰 늘 "최고 +0.0% / 최저 +0.0%" 가 된다(2026-08-12 실측) |
| 보유기간 | 진입(첫 매수 체결)부터 청산까지 얼마나 들고 있었는지를 화면·매매일지·요약·Discord 에 함께 적는다. **당일과 이월을 다른 단위로** 쓴다 — `47분` · `3시간 12분` · `2일차`. 벽시계 시간은 장중에는 정직하지만 밤·주말을 넘기면 거짓말이 되기 때문이다(금 15:20 매수 → 월 09:05 은 벽시계로 66시간이지만 실제 장중 노출은 6시간 남짓). `N일차` 는 **거래일** 기준이라 주말·휴장이 끼어도 어긋나지 않고, 옆 열의 기준봉이 이미 `D±n` 이라 형태를 달리했다. **2차 매수(물타기)는 시계를 되돌리지 않는다** — 답해야 하는 것은 "언제부터 들고 있나" 이므로 언제나 첫 매수가 기준이다. 진입 시각은 `events` 에서 유도하므로 따로 저장하는 값이 없다(이월돼도 며칠 전 매수를 그대로 집어낸다). **그날 매수한 것이 없으면 표시하지 않는다** — 조회가 최근 45일의 마지막 사이클을 집어 오므로, 며칠 전에 사고팔았던 종목을 오늘 관심종목으로 다시 등록하면 그때의 기간이 딸려온다(2026-08-26 실측: 대기 종목에 '26분' 이 떴다). 값이 없으면 다른 열과 같게 `-` 로 채운다. **체결통보 유실로 강제 복구된 포지션이나 등록 창에서 시작 상태를 직접 지정한 종목은 매수 기록이 없어 빈칸이다 — 추정하지 않는다** |

## 6. 아키텍처

매매 코어와 UI 는 스레드로 분리되어 서로를 블로킹하지 않는다. 코어는 백그라운드 스레드의 asyncio 루프에서 돌고, Tkinter UI 는 메인 스레드에서 돌며, 둘은 **큐 2개로만** 통신한다.

```
[코어 스레드 (asyncio)]
키움 WebSocket ──체결가(0B)──▶ Watcher ──가격 이벤트──▶ StateMachine
키움 WebSocket ──체결통보(00)─▶ Core   ◀──주문 지시──── StateMachine
                                 │                        │
                                 └──체결 확정──▶ 상태 확정 ─┤
                                                          ▼
                                        Store(SQLite) + Notifier(Discord)
                                                          │
[메인 스레드 (Tkinter)]                                    │
UI ◀────────────── 이벤트 큐 (상태·체결·로그) ──────────────┘
UI ─────────────── 명령 큐 (등록·수정·청산·설정) ──────────▶ 코어
```

| 모듈 | 역할 |
|---|---|
| **StateMachine** | 순수 로직(I/O 없음). 가격 → 상태 전이 + 주문 지시 반환. 단위 테스트의 핵심 대상 |
| **Watcher** | WebSocket 시세(0B)·체결통보(00) 수신, PING 응답, 지수 백오프 재연결 |
| **Broker** | 키움 REST 시장가 주문, 계좌·종목 조회, 체결통보 해석, **호출 간격 제어와 조회 재시도** |
| **Kiwoom** | 모의/실전 접속 정보, 접근토큰 발급·캐시·만료 전 자동 재발급 |
| **Core** | 전체 조립. 틱 → 판단 → 예수금·종목 수 방어 → 주문 → 체결 확정 → 저장·알림·화면 반영. 재연결 후 가격 보정과 잔고 대조도 담당 |
| **Store** | SQLite 영속화·복원 (매매일 단위). 상태 스냅샷 + 이벤트 이력 |
| **Notifier** | 알림 문구·embed 구성 + 알림 수준 필터 (순수 함수) |
| **DiscordBot** | 알림 발송·슬래시 명령·장중 대시보드 (코어와 같은 루프의 태스크) |
| **UI** | Tkinter. 코어의 구독자 중 하나로 비즈니스 로직이 없다. `after()` 기반 200ms 큐 폴링이라 틱 유입량과 무관하게 부하가 일정하다. 코어는 UI 존재를 모르므로 헤드리스 실행도 가능 |

### 명령 분배

UI·Discord 에서 온 명령은 `Core._handle_command` 가 **묶음별 처리기로 넘기기만** 한다.

| 처리기 | 맡는 것 |
|---|---|
| `_handle_position_command` | 수동 청산 · 포지션 이월 · 이월 · 리셋 — **잔량과 평단에 닿는 유일한 곳** |
| `_handle_symbol_command` | 등록(`_register`) · 삭제 · 조회 |
| `_handle_journal_command` | 기록 · 일지 · 차트 · 일일 요약 — 매매 판단과 무관 |
| `_handle_system_command` | 연결 · 감시 시작/중지 · 자금 · 모드 · 매매일 |

예전에는 한 함수에 21 가지가 다 들어 있어 **303줄**이었다(2026-08-27 분리). 일지 기능을
붙일 때마다 매수/매도 판정이 있는 자리를 함께 건드려야 했고, 실제로 이번 달에 그렇게
했다. 나눠 두면 손댈 곳이 분명해진다 — **포지션에 닿는 것은 첫 줄 하나뿐이다.**

명령은 모두 서로 다른 dataclass 라 분기 순서가 결과를 바꾸지 않는다. 새 명령을 추가할
때 어느 묶음인지 정하지 않으면 `test_모든_명령이_어느_묶음엔가_속한다` 가 걸린다 —
분배표에서 빠진 명령은 조용히 무시되어 눌러도 아무 일이 안 일어나기 때문이다.

## 7. 데이터 저장 (SQLite)

| 테이블 | 용도 |
|---|---|
| `symbols` | 관심종목과 종목별 설정 — **PK (매매일, 종목코드)**. 3선 가격, 매수 금액, 익절 %/비중, 메모, **선정 태그·기준봉 날짜** |
| `positions` | 종목별 상태 스냅샷 — **PK (매매일, 종목코드)**. 상태, 평단가, 최초 물량, 잔량, 실현손익, **거래비용**, **보유 중 최고/최저가**, 체결 대기 여부 — 장애 복구의 기준 |
| `events` | 상태 전이·주문·체결·에러 이력 (append-only) — 화면 로그 복원과 월간 통계의 원천. 체결 행에는 **판정가(trigger_price)와 실제 체결가**가 함께 남아 시장가 주문의 체결 오차를 나중에 집계할 수 있다 |
| `orders` | 주문 요청/체결 기록 (주문번호, 구분, 수량, 가격, 체결 결과) |
| `journal` | **매매일지** — 잘한 점·아쉬운 점과 보관된 차트 경로. 손익·MFE/MAE·태그는 이미 다른 테이블에 있으므로 여기에는 사람이 쓴 것과 파일 경로만 둔다 |
| `settings` | 전역 설정 key-value — 총 운용금액, 최대 종목 수, 1·2차 매수 금액, 익절 %/비중, 투자 모드, 알림 수준 |

- `events` 가 append-only 라 이후 pandas 로 읽어 월간 수익률, 상태별 체류 시간, 익절/손절 비율을 자유롭게 집계할 수 있다.
- DB 파일은 모드별로 분리된다: `data/trader-mock.db` · `data/trader-real.db`. 현재 모드는 `data/mode.txt` 에 저장한다(어느 DB 를 열지 정하려면 모드를 먼저 알아야 하므로 DB 밖에 둔다).
- 스키마 변경 시 `_SCHEMA_VERSION` 을 올린다(현재 **v15**). **컬럼 추가처럼 기존 데이터를 보존할 수 있는 변경은 `_MIGRATIONS` 에 등록해 자동 이관**되므로 DB 를 지우지 않아도 된다. 구조가 바뀌어 이관할 수 없는 경우에만 종전처럼 삭제 안내가 나온다. 구버전 DB 파일로 실행하면 버전 가드가 한글 에러로 안내하며, 개발 단계에서는 `data/` 의 DB 파일을 삭제하고 재실행한다.
- 시뮬레이터는 `simulator.db` 를 따로 써서 실전 데이터와 섞이지 않는다.

## 8. 로깅 · 알림 · 복기 차트

**로그** — 모든 이벤트(등록, 상태 전이, 주문, 체결, 에러, 재연결)는 SQLite `events` 에 기록되고 화면 로그 창에도 표시된다. 프로그램이 예기치 않게 종료돼도 **재시작하면 그날의 로그가 화면에 그대로 복원**된다. 로그 창 우클릭으로 화면 비우기(DB 이력은 보존)와 CSV 내보내기를 할 수 있다.

**Discord 알림** — 매매 이벤트는 사람이 읽기 쉬운 요약으로 발송된다.

```
🟢 성호전자(043260) 1차 매수 — 12주 @ 15,870          ← 한 줄 텍스트
💰 성호전자(043260) 1차 익절 — 4주 @ 16,330

┃ 💰 성호전자(043260) 종료                            ← 색 띠가 붙는 embed
┃ 1차 매수 → 3% 익절 → 5% 익절 → 7% 익절
┃ 세후 +8,406원 (+6.77%)
┃ 평단 15,870 → 청산 16,930 · 투입 19.0만원
```

- 주문 접수가 아니라 **체결 확정 시점**에만 발송하며, 종료 시 결산이 함께 표시된다
- **CSV 불러오기는 조용하다.** 편성 결과는 08:55 개장 브리핑이 맡고, 언제든 `/관심종목` 으로 볼 수 있다. 다만 **등록 경고**(3선 순서 위반, 매수 금액으로 1주도 못 사는 종목 등)는 사용자가 고쳐야 하는 문제라 즉시 알린다 — 이때도 **경고만** 보낸다. 한 건 때문에 80종목 목록이 폰으로 쏟아지면 정작 고쳐야 할 한 줄이 그 안에 묻힌다(2026-08-31 실측)
- 일일 요약에는 **진입 못 한 종목**을 사유별로 나눠 **전부** 싣는다 — 최대 종목 수, 예수금 부족, 매수 수량 0주 등. 1선에 닿았는데 끝내 못 산 종목이고, 나중에 자리가 나서 들어간 것은 뺀다. 사유가 섞이면 자금을 늘려야 할지 종목 수를 늘려야 할지 알 수 없어 사유마다 필드를 나눈다. 개수를 자르지 않는 이유는 이 목록 자체가 '몇 개나 놓쳤나' 에 답하기 때문이다(2026-09-02 실측: 최대 종목 수에 막혀 5종목을 놓쳤다). **근접도 목록에서는 뺀다** — 보류 종목은 1선을 이미 지나 괴리율이 음수라 '내일 볼 만한 종목' 맨 위를 차지해 버린다
- 종료 알림은 **경로 · 세후 손익 · 가격대 · 보유기간**을 담는다. 잔량 주수는 "그래서 어땠나" 에
  답하지 않고, **수익률(%)** 이 없으면 금액만으로는 큰 손실인지 알 수 없다(저가주는
  주식 수가 많아 절대액이 커 보인다). 청산가는 마지막 체결가가 아니라 **평균 청산가**다 —
  3단 익절을 하면 판 가격이 제각각이라 마지막 한 건으로는 답이 되지 않는다
- **알림 수준**: `전체` / `매매만 (시스템 제외)` / `에러만` / `끔` — 화면에서 즉시 변경되고 설정에 저장된다
- **매매일지**: 종목이 '종료' 되면 복기 차트가 `data/journal/2026-08/2026-08-10/` 아래
  `종목코드-종목명-익절-daily.png` 형태로 보관된다(탐색기에서 정렬만 해도 손절 매매가 모인다).
  일지 목록은 **매매 사이클 단위**다 — 이월된 포지션이 여러 매매일에 걸쳐 있어도 종료된 날
  한 건으로 묶인다(같은 매매를 여러 번 쓰지 않도록). 각 항목에는 **상태 경로**
  (`2차 매수 → 3% 익절 → 본절 이탈`)와 **진입·청산 시점**(시각·기준봉 D±n 포함), **보유기간**이
  함께 표시된다 — `진입 2026-08-07 09:14 (D+1) · 청산 2026-08-12 13:02 (D+4) · 보유 4일차`.
  표의 '보유' 열은 경과만 보여 주므로 언제 들어갔는지는 여기서 확인한다.
  경로에는 '대기' 와 '종료' 를 적지 않는다 — 대기는 모든 매매의 출발점이라 정보가 없고,
  '종료' 대신 **끝난 이유**(7% 익절 / 본절 이탈 / 손절 / 수동 청산 / 진입 금지)를 적어야
  무엇 때문에 끝났는지 알 수 있다. '1차 매수 → 2차 매수' 는 '2차 매수' 로 줄인다.
  목록은 **익절 빨강 / 손절 파랑 / 본전·보유 회색**으로 칠해 결과가 한눈에 갈리고,
  코멘트를 쓴 줄에는 `✔` 가 붙는다(손익 아이콘은 부호·색과 겹쳐 없앴다).
  목록 위 **검색창**(종목명·코드 일부, `Ctrl+F` 로 포커스), **기간 선택**(월별 또는 전체
  — 둘 중 하나), **전체/익절/손절** 버튼으로 걸러 볼 수 있다. 익절·손절은 수수료·세금까지
  뺀 **세후 손익 부호**로 나눈다. 목록 아래에는 그 기간의 성적이
  `20건 · 익절 15 · 손절 5 · 승률 75.0% · 세후 +115,000원` 처럼 한 줄로 나온다
  (승률의 분모에서 본전·보유 중인 건은 뺀다). 기간은 **DB 단계에서** 자르고 기본은
  이번 달이다 — 전부 읽어와 화면에서 거르면 기록이 쌓일수록 창이 뜨는 데 오래 걸리고,
  그 조회가 코어 스레드에서 돌아 매매 판정까지 밀린다.
  차트는 **휠로 확대·축소, 드래그로 이동**한다 (더블클릭하면 원본 뷰어로 열린다).
  코멘트는 툴바 **[매매일지]** 또는 로그 우클릭 → **매매일지 열기**에서 차트를 보며 작성한다 — 종료 직후·장중·
  마감 후·주말 어느 때나. 미작성 건은 일일 요약에 안내된다
- **시장 대비**: 일일 요약에 **내 종목 등락률 · 관심종목 평균 · KOSPI** 를 나란히 보여준다.
  감시 중 받은 첫 체결가와 마지막 체결가로 계산하므로 추가 조회가 없다
- **증권사 대조**(15:35, 읽기 전용): 체결 내역·거래비용은 ka10076 으로 한 번에, **세후 실현손익은 ka10077 로 오늘 매도가 있었던 종목마다 한 번씩** 조회해 맞춰 본다. ka10077 은 계좌 전체를 주는 TR 이 아니라 **종목 단위**다 — 인자 없이 부르면 서버가 `필수입력 파라미터=stk_cd` 로 거절하고, 조회 실패는 조용히 넘어가는 설계라 대조가 매일 통째로 건너뛰어진다(2026-08-19 ~ 08-21 실제로 그랬다). 한 종목이 실패해도 나머지는 진행하고, 전부 실패했을 때만 대조를 건너뛴다 — 일부만 받은 값으로 합계를 비교하면 없는 차이를 만들어 낸다
- **일일 요약**(기본 15:35): 체결 건수, 세전·세후 실현손익, 종목별 결과(최고/최저 도달률·**보유기간**), **이월이 필요한 보유 종목**, 계좌 평가손익·추정자산, 주문가능금액을 한 번에 정리해 보낸다. Discord embed 로 발송해 **세후 손익 부호에 따라 초록/빨강 색 띠**가 붙고 종목마다 항목이 나뉜다(💰 이익 / 🛑 손실 / ⚠️ 이월 필요)
- **메시지 층위**: 자주 오는 것은 가볍게, 중요한 것은 눈에 띄게 나눈다.
  **매수·단계 익절**만 한 줄 텍스트로 보내고, 나머지는 모두 색 띠가 붙는 embed 다 —
  **종목 종료(손절·청산)** 는 세후 손익 부호에 따라 초록/빨강, **에러**는 빨강,
  **경고·보류**는 주황, **연결·감시·시작**은 청록, **등록·편집·삭제·설정·이월**은 청회색.
  종류마다 아이콘도 다르다(⛔ ⚠️ ⏸️ ➕ ✏️ 🗑️ ⚙️ 📦 🔗 👁️ 🚀 📊).
  Discord 는 같은 웹훅의 연속 메시지를 한 덩어리로 묶어 보여주기 때문에, 색 띠가 없으면
  경고가 체결 알림 사이에 묻힌다
- **오류 문구 정리**: API 오류의 기술적 부분(`kt10000 실패 (HTTP 200, code 20): [2000]`)을
  걷어내고 사람이 읽을 내용만 남긴다 — "주문 실패(3회): 매수증거금이 부족합니다. 127주 매수가능"
- **관심종목 편성은 조용히**: 등록·편집·삭제·리셋·이월과 CSV 불러오기 결과는 저녁에 PC 앞에서
  몰아서 하는 작업이라 건건이 알리면 소음이 된다. 화면 로그와 DB 에는 남기되 **Discord 로는
  보내지 않고**, 08:55 개장 브리핑으로 갈음한다. 다만 **등록 실패**(1선 > 2선 > 3선 위반 등)는
  사용자가 고쳐야 하는 문제라 즉시 알린다
- **개장 브리핑**(감시 시작 시): 오늘 무엇을 들고 시작하는지 한 장으로 — 종목 수, **태그 분포**,
  **기준봉 경과일 분포**, 자금 설정, 주문가능금액, 소량 진입이 예상되는 종목. 개별 종목을
  나열하면 수십 줄이 되므로 집계로 보여준다 (전체 목록은 `/관심종목`) 상태·잔량 같은 기계적 정보 대신 "무엇을 왜 골랐는지" 를
  남기는 자리이기 때문이다. 등록에 실패한 종목은 주황색 필드로 분리된다
- **묶음 알림**: 등록·편집·삭제·보류·경고처럼 한 번에 여러 건이 쏟아지는 정보성 알림은 2초간 모았다가 **embed 한 장**으로 보낸다(경고는 별도 필드로 분리·주황색). CSV 로 24종목을 넣어도 발송이 1회로 끝나고, 그 뒤에 오는 체결 알림이 밀리지 않는다. **체결 알림(매수·익절·손절)은 즉시성이 중요하므로 묶지 않고 한 줄로** 바로 보낸다
- 발송 제한은 discord.py 가 자체 큐로 처리한다. 그래도 알림이 많으면 읽기 어려우므로 평소에는 **'매매만'** 을 권장한다

**복기 차트** — 매매를 되돌아보기 위한 PNG 차트 2종을 자동 생성한다.

| 차트 | 구성 |
|---|---|
| 일봉 (세로 3:4) | 4패널 — 일봉 60봉(속 빈 캔들 + 이평 5·10·20·60·120) / 거래량(속 빔) / 거래대금(채움, 단위 자동 보정) / KOSPI(캔들 + 이평 10·20). 1·2·3선 마젠타 수평선(가격은 오른쪽 끝 태그), 현재가 태그, **월 단위 세로 격자**, 진입▲·청산▼ 마커(**캔들 밖** — 매수는 저가 아래, 매도는 고가 위. 겹치면 위아래로 쌓는다) |
| 3분봉 (세로 3:4) | 진입 마커는 **매매 사이클 전체의 체결**에서 찍는다 — 이월 종목은 매수가 며칠 전이라 당일 기록만 보면 진입 화살표가 빠진다. **최소 2거래일**(짧게 보유한 종목도 캔들이 충분하도록), 며칠 보유한 이월 종목만 진입일부터 전부. **그날 누적 최저가** 대비 3/5/7% 검정 계단 지표(날마다 리셋). 익절 트리거는 **평단 대비**라 기준점이 다르다 — 숫자가 같아도 의미가 다른 선이다, 날짜 경계선, 3선·마커 동일 |

- **📈 버튼**: 클릭 → 백그라운드 생성(1~3초) → 일봉/3분봉 탭 창으로 표시. **휠로 확대·축소, 드래그로 이동**하고(보이는 영역만 리샘플링해 배율과 무관하게 비용이 일정하다), 더블클릭으로 원본 뷰어, "Discord로 보내기" 버튼으로 전송
- **종료 시 자동 전송**: 매매가 있었던 종목이 '종료' 되면 차트 2장이 Discord 로 자동 발송된다
- 생성·조회는 전부 백그라운드 스레드 + 무화면(Agg) 렌더링이라 **매매 판정을 지연시키지 않는다**. PNG 는 `data/charts/매매일/` 에 남는다
- 한글 폰트는 맑은 고딕이 기본이며, `[chart] font` 로 교체할 수 있다(나눔고딕, Pretendard 등 설치 후 이름 기입)
- TR 규격 실측 확인: `uv run check_kiwoom.py 005930 --chart`

**Discord 봇** — 알림 발송·슬래시 명령·대시보드가 모두 봇 하나로 나간다(웹훅은 쓰지 않는다 —
발송 경로가 둘이면 "지금 무엇이 연결된 상태인지" 가 헷갈려 운영 사고로 이어진다).
`config.toml` 에 `bot_token`·`channel_id`·`allowed_users` 를 채우면 **프로그램 시작과 함께
자동 연결**된다. 비워두면 Discord 없이 동작하며 화면 로그와 DB 기록은 그대로 남는다.

| 명령 | 동작 |
|---|---|
| `/상태` | 보유 종목·평단·현재가·수익률·보유기간, 실현손익, 계좌 평가·추정자산, 주문가능금액 |
| `/주문가능` | 지금 더 매수할 수 있는 금액 조회 |
| `/요약 [날짜]` | 매매 요약 조회 (날짜를 비우면 오늘, 기록이 있는 날짜가 자동완성된다) |
| `/근접도` | 미진입 종목이 1선에 얼마나 가까운지 (가까운 순) |
| `/관심종목 [태그] [쪽]` | 오늘 관심종목의 태그·메모·기준봉 (태그 필터·페이지, 실제 쓰인 태그가 자동완성된다) |
| `/차트 [종목]` | 복기 차트를 만들어 **이 채널로** 전송 (입력하면 종목 후보가 자동완성된다) |
| `/감시 [시작·중지]` | 감시 제어 |
| `/알림 [수준]` | 전체 / 매매만 / 에러만 / 끔 |

- **결과는 명령을 낸 자리로 돌아간다.** 📈 버튼은 UI 창, Discord 명령은 Discord 채널로
  전송된다. 상태를 바꾸는 명령(`/감시`·`/알림`)은 코어에 실제로 반영된 것을 확인한 뒤
  답하므로, 거부된 경우(키움 미연결 등)를 놓치지 않는다
- **주문을 내는 조작(수동 청산·종목 삭제·설정 변경)은 일부러 넣지 않았다** — 계정이 탈취돼도
  최악이 '감시가 꺼지는 것' 에 그치게 하기 위해서다. 그런 판단은 미니PC 에서 직접 한다
- **화이트리스트**: `allowed_users` 에 등록된 사용자가 지정 채널에서 보낸 명령만 실행된다.
  비워두면 봇이 켜지지 않는다(안전한 기본값)
- **장중 대시보드**: 감시 시작 시 메시지를 만들어 채널에 고정하고 10초마다 **편집**으로
  갱신한다(새 메시지가 아니라 편집이라 채널이 더러워지지 않고 푸시도 울리지 않는다).
  일일 요약이 나가면 고정을 풀고 삭제해, 장 마감 후에는 요약만 남는다.
  고정에는 채널 **'메시지 관리'** 권한이 필요하며, 없으면 고정만 실패하고(로그로 알림)
  대시보드 자체는 정상 동작한다. Discord 의 고정 메시지는 채널 상단에 상주하지 않고
  **핀 아이콘 목록**에서 확인한다
- **Discord 연결과 키움 연결은 별개다.** 봇이 붙어도 키움이 끊겨 있으면 매매가 되지 않으므로,
  대시보드는 그 경우 주황색으로 "⛔ 키움 연결 안 됨" 을 맨 위에 띄운다
- 봇은 코어와 같은 asyncio 루프에서 태스크로 돌며, 상태는 직접 읽되 **변경은 UI 와 똑같이
  명령 큐를 통해서만** 한다. 봇 연결이 끊겨도 웹훅 알림은 계속 나간다 (캔들이 HTS 와 다르면 `--raw` 로 응답 원본 필드까지 확인)

### 매매일지 문서 내보내기

```
uv run python export_journal.py                # 가장 최근 매매일
uv run python export_journal.py 2026-08-21     # 그날만
uv run python export_journal.py --month 2026-08
uv run python export_journal.py --all
uv run python export_journal.py --mock         # 모의투자 기록
```

DB 는 **프로그램과 같은 규칙**으로 고른다 — `data/mode.txt` 를 읽어 실전이면
`trader-real.db`, 모의면 `trader-mock.db`. `--real` / `--mock` 으로 덮어쓰거나
`--db 경로` 로 직접 지정할 수 있다.

매매 프로그램과 **따로 도는 읽기 전용 도구**라 장중에 돌려도 안전하다. 결과는 이렇게 쌓인다.

```
journal/2026-08/
  2026-08-21.md                       ← 그날 인덱스 (성적 + 매매 목록 + 각 문서 링크)
  2026-08-21/
    263800-데이타솔루션.md             ← 매매 1건 = 파일 1개 = 나중에 A4 1장
    263800-데이타솔루션-daily.png      ← 일봉 (문서 옆으로 복사)
    263800-데이타솔루션-minute.png     ← 3분봉
```

**차트는 일봉과 3분봉을 둘 다 싣는다.** 일봉은 3선을 어디에 그었는지(선정 근거)를,
3분봉은 그날 어떻게 체결됐는지(실행)를 보여준다 — 복기의 질문이 서로 달라 한쪽만으로는
답이 나오지 않는다. 원본이 지워졌으면 있는 것만 싣는다.

**매매 사이클 하나에 문서 하나**이고, **청산된 날에만** 만든다. 월요일 매수 → 화요일
1차 익절 → 수요일 전량 매도면 수요일 문서 하나뿐이다. 날짜별로 만들면 같은 매매의
문서가 셋으로 갈라져 어느 것이 완성본인지 알 수 없고, 아직 끝나지 않은 매매에
'미작성' 표시가 계속 쌓여 정작 안 쓴 것이 묻힌다.

손익은 **사이클 전체를 합산**한다. 스키마 v12 에서 손익을 날짜별로 쪼갠 뒤라 청산일
행만 쓰면 전날 낸 1차 익절이 빠진다.

문서는 순수 생성물이라 **다시 돌리면 통째로 덮어쓴다**. 그래야 나중에 코멘트를 채운 뒤
다시 돌려 반영할 수 있다. 다만 **청산된 매매의 문서는 그 뒤로 바뀌지 않는다** — 보유
중인 매매가 없으므로 보유기간이 자라 매일 커밋이 생기는 일도 없다.

**담지 않는 것: 예수금·계좌 평가액·주문가능금액.** 종목·손익액·손익률은 남긴다 —
그것까지 빼면 복기가 되지 않는다.

### 폰에서 복기하기 (git 동기화)

미니PC 는 모니터가 없어 원격 접속으로만 화면을 본다. 매매는 09:00~15:30 에만 일어나지만
복기는 아무 때나 하고 싶은 일이라, **문서를 git 에 올려 두고 폰에서 읽는다**. private
저장소에 올라가 있으므로 **미니PC 가 꺼져 있어도** 볼 수 있다.

**한 번만 하는 준비**

1. GitHub 에서 **private** 저장소를 만든다 (예: `three-line-journal`). public 으로 만들면
   매매 기록이 전부 공개된다.
2. 프로그램 폴더에서 저장소를 연결한다.

```
git init
git remote add origin https://github.com/<계정>/three-line-journal.git
git branch -M main
```

3. 첫 문서를 만들어 올린다.

```powershell
.\sync_journal.bat --all
```

**매일 하는 일** — 없다. 아래 자동 실행을 걸어 두면 손댈 일이 없다.

```powershell
.\sync_journal.bat            # 손으로 돌릴 때
```

> **PowerShell 에서는 앞에 `.\` 를 붙인다.** PowerShell 은 보안상 현재 폴더의 실행
> 파일을 자동으로 찾지 않아서, 그냥 `sync_journal.bat` 이라고 치면
> `CommandNotFoundException` 이 난다. `cmd.exe` 에서는 `.\` 없이도 된다.

문서 생성 → 변경 확인 → 커밋 → 푸시를 한 번에 한다. 문서 생성이 실패하면 git 은
건드리지 않고, 바뀐 것이 없으면 커밋도 만들지 않는다.

**인자를 주지 않으면 `--all`** 로 돈다. 지난주 매매의 일지를 오늘 고치는 일이 흔한데,
최근 하루만 다시 만들면 그 문서는 옛날 내용 그대로 남기 때문이다. 내용이 같은 파일은
건드리지도 커밋하지도 않으므로 전체를 돌려도 비용이 거의 없다.

**15:40 자동 실행** — 작업 스케줄러에 등록한다. `start.bat` 과 같은 방식이다.

1. 작업 스케줄러 → **작업 만들기** (기본 작업 아님)
2. 일반: 이름 `매매일지 동기화`, **사용자가 로그온할 때만 실행**
   (git 자격 증명이 사용자 프로필에 있어서, 로그오프 상태로 돌리면 푸시가 실패한다)
3. 트리거: 매일 **15:40** — 요약 발송(15:35)과 겹치지 않게 둔다
4. 동작: 프로그램 시작 → 프로그램 `sync_journal.bat`,
   시작 위치에 **프로그램 폴더 경로**를 반드시 넣는다
5. 조건: '컴퓨터를 AC 전원으로 사용할 때만 실행' 해제

휴장일에 돌아도 문제없다 — 새 매매가 없으니 "바뀐 것이 없습니다" 하고 끝난다.

**돌았는지 확인하려면** `data/sync_journal.log` 를 본다. 작업 스케줄러의 '마지막 실행
결과' 는 `0x0` / `0x1` 뿐이라 왜 실패했는지가 안 나오고, 자동 실행에는 콘솔이 없어
화면에 뜬 내용도 사라진다. 한 줄씩 이렇게 쌓인다.

```
2026-08-24 15:40:03  푸시 완료 — 4 files changed, 82 insertions(+)
2026-08-25 15:40:02  변경 없음 — 커밋하지 않음
2026-08-26 15:40:05  커밋 완료 · 푸시 실패 — could not resolve host: github.com
```

'작업이 안 돈 것' 과 '돌았는데 바뀐 게 없는 것' 이 구분된다. `data/` 라 커밋되지 않고,
최근 200줄만 남는다.

**15:40 이후에 일지를 고쳤다면** 손으로 한 번 더 돌리면 된다. 저녁에 고치든 주말에
고치든 마찬가지다.

```powershell
.\sync_journal.bat
```

### 프로그램 자동 실행

**시작프로그램에는 `start.vbs` 를 넣는다.** `shell:startup` 폴더에 바로가기를 두면
로그온할 때 **콘솔 창 없이** 뜬다. Tkinter 창은 그대로 나온다 — 그게 본체다.

콘솔이 없으면 기동 실패를 볼 수 없으므로 표준 오류를 `data/startup.log` 에 남긴다.
아침에 프로그램이 없으면 여기부터 본다.

**트레이 아이콘**은 오른쪽 아래 **상태 점**으로 지금 상태를 알린다 — 초록 감시 중,
회색 중지, 빨강 감시 중인데 시세가 안 옴. 아이콘이 16~32px 로 줄어드는 자리라 글자도
모양도 구분되지 않아 색만 남기 때문이다. 마우스를 올리면 **실전/모의 · 감시·보유 종목 수
· 마지막 틱 시각**이 뜬다. 창을 안 보고도 알아야 할 것만 담았고, 손익은 넣지 않는다 —
마우스를 올릴 때마다 금액이 눈에 들어오면 복기가 아니라 조바심이 된다.

오른쪽 클릭 메뉴는 **열기 · 폴더 열기 · 종료** 다. '폴더 열기' 는 창을 트레이에 내려 둔
채로도 `data/` 의 로그와 `journal/` 문서를 볼 수 있게 한다.

**창의 ✕ 는 종료가 아니라 트레이로 내리는 것이다.** 모니터 없는 미니PC 를 원격으로
조작하다 ✕ 를 잘못 누르면 그날 매매가 통째로 멈춘다(2026-09-02 실제로 겪음). 진짜
종료는 **트레이 아이콘 오른쪽 클릭 → 종료** 에만 둔다 — 실수로 닫는 경로와 일부러 끄는
경로가 같은 자리에 있으면 의미가 없다. 트레이를 만들 수 없는 환경에서는 ✕ 가 평소대로
종료로 남는다.

**감시 시작/중지 버튼은 확인창을 거친다.** 바로 옆이 '매매일지' 라 오클릭이 나고,
장중에 실수로 중지되면 그날 매매가 멈춘다. 중지 확인창은 기본 선택이 '아니오' 라
엔터를 잘못 쳐도 멈추지 않고, 보유 중인 종목이 몇 개인지 함께 알린다.

> **자동 스케줄은 확인창을 거치지 않는다.** 08:55 자동 시작과 15:30 자동 중지는 코어가
> 스스로 하는 것이라 UI 를 지나지 않고, Discord `/시작`·`/중지` 도 마찬가지다. 사람이
> 없을 때 확인창이 떠서 스케줄이 막히면 안 된다 — 테스트가 이 경계를 지킨다.


`start.bat` 을 **앱 > 시작프로그램**에 넣어 두면 로그온할 때 뜬다. 다만 그것만으로는
빈틈이 있다 — 시작프로그램은 **로그온할 때 한 번**만 돌아서, 미니PC 를 며칠 켜 둔 채
프로그램만 죽으면 재부팅 전까지 멈춰 있다. 밤사이 윈도우 업데이트가 재부팅해 로그인
화면에서 대기 중이면 아침에 아예 안 켜진다.

그래서 작업 스케줄러에 **안전망**을 하나 더 둔다.

1. 작업 만들기 → 이름 `3선 자동매매 안전망`
2. 일반: **사용자가 로그온할 때만 실행** — Tkinter 창이 보이려면 대화형 세션이어야
   한다. '로그온 여부에 관계없이 실행' 으로 걸면 세션 0 에서 돌아 **창이 안 보인다**
3. 트리거: **매주 · 월~금 · 08:50** (매일로 하면 주말에도 헛돈다).
   고급 설정의 **임의 지연은 켜지 않는다** — 최대 1시간 밀려 장 시작 뒤에 뜰 수 있다
4. 동작: 프로그램 `start.bat`, **시작 위치에 프로그램 폴더 경로**
5. 설정: **'예약 시작 시간을 놓친 경우 가능한 한 빨리 작업 실행'** 체크.
   **'작업이 실패하면 다시 시작' 은 켜지 않는다** — 중복 실행으로 종료될 때도 실패로
   잡혀 무한히 재시도한다
6. 조건: 'AC 전원일 때만 실행' 해제

`start.bat` 은 포트 47321 을 먼저 확인해 **이미 돌고 있으면 창 없이 끝낸다.** 두 경로가
겹쳐도 오류 창이 쌓이지 않고, 이중 주문은 `main.py` 의 잠금이 막는다.

> 원격 접속을 끊을 때는 **'연결 끊기'** 를 쓰고 **로그오프하지 않는다.** 로그오프하면
> 세션이 사라져 프로그램이 같이 죽고, 대화형 세션이 없어 08:50 안전망도 뜨지 않는다.

> **배치 파일에는 한글을 넣지 않는다.** cmd.exe 는 배치 파일을 **바이트 위치를 기억하며**
> 한 줄씩 읽는다. `chcp 65001` 로 코드페이지를 바꾸면 그 뒤 한글(3바이트)의 위치 계산이
> 어긋나 주석 끝의 마침표가 명령으로 튀어나온다 — 탐색기 더블클릭이든 PowerShell 이든
> `'.' is not recognized as an internal or external command` 가 뜬다(2026-08-23 실측).
> 줄바꿈이 LF 여도 여러 줄 `if (...)` 블록을 잘못 끊는다. 그래서 `.bat` 은 **ASCII + CRLF**
> 로만 두고(`.gitattributes` 가 고정한다), 한글과 판단은 전부 `.py` 쪽에 둔다.
> `tests/test_sync_journal.py` 가 이 규칙을 검사한다.

편이 깔끔하다.

### Discord 로 매매일지 쓰기

종료된 매매마다 `#매매일지` 채널에 스레드가 하나 생긴다(`08-24 데이타솔루션 손절`).
거기에 **평소 채팅하듯 답글을 달면** 일지가 된다.

```
호가가 얇아 슬리피지 컸음        ← 접두어 없음 → 아쉬운 점
+ 손절 규칙 그대로 지킴          ← 잘한 점
물타기 유혹 참음                 ← 앞의 '+' 가 이어져 잘한 점
```

접두어를 만나면 칸이 바뀌고 다음 접두어까지 이어진다. `잘한 점:` / `아쉬운 점:` 도
그대로 받는다. `-` 는 쓰지 않는다 — Discord 가 글머리 기호로 렌더링해 버린다.

**슬래시 명령과 버튼은 쓰지 않는다.** 그것들은 봇이 켜져 있어야만 동작해서 미니PC 가
꺼져 있으면 "상호작용에 실패했습니다" 가 뜬다. 일반 답글은 봇이 죽어 있어도 서버에
남아 있다가 다음 기동 때 들어온다. **사용자는 봇 상태를 신경 쓸 필요가 없다.**

수정·삭제는 Discord 기본 기능을 그대로 쓴다. 봇이 매번 **스레드 전체를 다시 읽어**
일지를 처음부터 만들기 때문에, 몇 번을 돌려도 결과가 같고 편집도 삭제도 따라온다.

DB 까지만 들어간다. 문서와 git 커밋은 **다음 15:40 동기화** 때 함께 반영된다 — 답글마다
커밋하면 하루에 수십 개가 생기고, 자동화를 일일 요약에서 끊는다는 원칙도 깨진다.
급하면 `.\sync_journal.bat` 을 손으로 돌린다.

**스레드에 담기는 것.** 종료 embed 에 **선정 근거와 시간축**을 덧붙인다 —
`진입 09:05 · 청산 09:41 · 기준봉 08-19 (D+5)` 와 태그. 코멘트를 쓰려면 "왜 골랐나" 와
"얼마나 들고 있었나" 가 눈앞에 있어야 한다. 알림 채널로 가는 종료 embed 는 짧게 둔다 —
장중에 흘려보는 알림이라 길면 방해가 된다. 최고/최저(MFE/MAE)는 **일부러 넣지 않는다**;
숫자가 늘수록 무엇을 보고 쓸지 흐려지고, 그 값들은 문서에서 차분히 본다.

**종료 차트(일봉·3분봉)는 스레드 안으로 간다.** 복기할 때 보는 것이라 답글을 다는 자리
바로 위에 있어야 채널을 오가지 않는다. 스레드가 없으면 알림 채널로 물러난다 — 차트가
아예 사라지는 것보다 낫다. `/차트` 로 직접 부른 것은 지금 보려는 것이므로 평소대로
알림 채널로 간다.

**UI 일지 창과의 관계 — 일지는 스레드에 보이는 그대로다.** 봇이 올린 UI 내용이 맨 위,
그 뒤에 답글이 순서대로 이어진다. 답글을 지우면 일지에서도 사라지고, UI 내용은 봇
메시지에 남아 있으므로 그대로 남는다. 화면과 일지가 어긋나지 않는 것이 이 규칙의 값이다.

**답글이 한 번이라도 달리면 그 뒤로 UI 저장분은 스레드에 올라가지 않는다**(`replied`,
스키마 v15). 계속 고쳐 쓰면 답글에서 읽은 내용이 그 메시지로 되돌아와 같은 문장이 두 번
세어진다. 그 시점의 UI 내용으로 고정된다고 보면 된다.

둘을 계속 합치는 쪽은 택하지 않았다. UI 창에는 늘 '합쳐진 전체' 가 보이는데 거기서
저장하면 답글 내용까지 봇 메시지로 들어가고, 다음에 읽을 때 두 번 세어진다. 막으려면
문장마다 출처를 추적해야 하고, 그러면 자유롭게 고칠 수 없게 된다 — 자유 서술로 정한
취지와 어긋난다.

**UI 일지 창과의 관계.** UI 에서 저장하면 봇이 스레드에 메시지 하나를 두고 그것을
고쳐 쓴다 — 폰에서 그 내용을 보고 이어서 쓸 수 있다. 다만 **한 번이라도 답글을 달면
그 뒤로는 스레드가 일지의 주인**이 된다. 둘을 합치려 들면 UI 에서 저장할 때마다 답글이
접혀 들어가 중복되므로 어느 한쪽이 주인이어야 한다. UI 로 쓴 내용은 스레드에 메시지로
남아 있으니 필요하면 복사해 답글로 옮기면 된다. 답글이 없는 동안은 UI 쪽이 그대로 산다.

되먹임은 세 층으로 막는다 — ① 작성자가 봇인 메시지는 읽지 않는다 ② `mirror_message_id`
와 대조한다 ③ 본문 첫 줄의 표식으로 거른다. 한 겹이면 충분해 보이지만 봇 토큰을 갈거나
DB 가 지워지면 판정이 어긋난다. 그때 **조용히 무한 루프가 도는 대신 멈추도록** 세 층을
둔다. 올린 내용인지의 판정은 시각이 아니라 **본문의 지문**으로 한다 — 시각으로 비교하면
스레드에서 읽어 온 내용이 곧바로 '아직 안 올린 것' 으로 잡혀 되먹임이 생긴다.

> **채널 권한을 먼저 준다.** 비공개 채널은 역할별로 접근을 따로 허용해야 해서, 봇이
> 목록에 없으면 채널은 보이는데 전송만 막힌다 — 청산할 때마다 `50001 Missing Access`
> 가 나고 그날 청산된 종목이 전부 스레드 없이 지나간다(2026-08-26 실측). 채널 편집 →
> 권한에서 봇에게 **채널 보기 · 메시지 보내기 · 공개 스레드 만들기 · 스레드에서 메시지
> 보내기 · 메시지 기록 보기 · 링크 첨부** 를 허용한다. 시작할 때 확인해 부족하면
> 알리고, 스레드가 없는 청산 매매는 **기동할 때 메운다** — 대상은 **최근 5 매매일**이다. 개수만 제한하면 재시작할 때마다 그다음 오래된 것을 만들어 몇 달 전까지 거슬러 올라간다(2026-08-27 실측). 며칠 지난 매매는 이미 복기가 끝났거나 문서로 보는 것이다. 답글 내용이 그대로면 아무것도 하지 않는다 — 기동할 때마다 스레드를 다시 읽으므로 걸러 내지 않으면 답글을 단 종목 수만큼 '일지가 갱신됐습니다' 로그가 매번 쌓인다(2026-08-26 실측). **이미 만들어진 스레드의 첫 메시지도 최신 형식으로 고쳐 쓴다** — embed 에 담는 내용을 바꿔도 예전 스레드가 옛 모습으로 남으면 며칠 전 매매를 복기할 때 정보가 빠진다. 내용이 같으면 건드리지 않는다.

> **`message_content` 인텐트가 필요하다.** 답글 본문을 읽으려면 Discord 개발자 포털의
> 봇 설정에서 **Message Content Intent** 를 켜야 한다. 지금은 채널 조회에 필요한
> `guilds` 만 켜져 있다.

## 10. 개발과 테스트

> **Tk 루트는 프로세스에 하나만.** 테스트마다 `tk.Tk()` 를 새로 만들면 두 번째부터
> Tcl 인터프리터가 하나 더 생기는데, 윈도우에서는 그때 라이브러리를 다시 읽으려다
> 실패해 UI 테스트가 건너뛰어진다(`couldn't read file .../text.tcl`). 파이썬을
> 재설치해도 그대로였고, 실행마다 건너뛰는 개수가 1~2개로 오갔다 — 파일이 없어서가
> 아니라 **앞선 루트가 남아 있느냐**가 갈랐다는 뜻이다(2026-09-05). `tests/conftest.py`
> 의 `tk_root` 는 살아 있는 루트가 있으면 빌려 쓰고, 테스트가 남긴 루트는 자동으로
> 정리한다. 새 UI 테스트를 쓸 때는 `tk.Tk()` 대신 이 픽스처를 받는다.

```bash
uv run pytest              # 전체 테스트
uv run pytest -v           # 테스트별 결과 표시
uv run pytest -rs          # 생략(skip)된 테스트와 사유 표시
```

- UI 스모크 테스트는 **실제 Tk 창을 띄워** "버튼을 눌러도 아무 반응이 없는" 유형의 버그를 잡는다. 화면이 없는 환경(CI 등)에서는 자동으로 생략되므로, 개발 PC 에서 돌리는 편이 좋다.
- 상태 머신은 순수 함수라 I/O 없이 전 시나리오를 검증한다. 매매 규칙을 바꿀 때는 여기부터 고친다.
- 키움 응답 필드는 개정될 수 있어 상수로 격리하고 방어적으로 파싱한다. 실측으로 확인된 케이스는 테스트로 고정해 둔다.
- **실전에서 겪은 사고는 반드시 회귀 테스트로 남긴다.** 예수금 필드 오독, 체결통보 유실, CSV 종목코드 누락, 화면 갱신 중단 등은 모두 그렇게 고정돼 있어 같은 문제가 다시 나지 않는다.
- **목록은 손으로 적지 말고 코드에서 뽑는다.** `test_ui_dispatch.py` 는 코어가 보내는 이벤트를 `core.py` 에서 찾아 전부 처리해 본다 — 손으로 적으면 이벤트가 늘었을 때 시험이 따라가지 못하고, 실제로 그 틈에서 사고가 났다(2026-08-13).
- **플랫폼에 따라 갈리는 부분은 Windows 에서 한 번 더 확인한다.** 개발·검증은 Linux 에서도 되지만, 키 이름(`<ISO_Left_Tab>`)·IME 조합 창·`os.startfile` 처럼 한쪽에만 있는 것들은 테스트를 통과해도 실제로는 깨진다.

## 11. 운영 메모 (실측 기반)

실제 운용에서 확인된 주의사항이다.

| 항목 | 내용 |
|---|---|
| **REST 호출 한도** | 키움 REST 는 초당 호출 수 제한이 있다. 재연결 직후 전 종목 시세를 간격 없이 조회하면 상당수가 거부된다(2026-07-24 실측: 22종목 중 10종목 실패). Broker 가 최소 간격(0.25초)과 조회 재시도를 처리하며, **주문은 재시도하지 않는다** — 응답만 유실되고 주문은 접수됐을 수 있어 중복 주문 위험이 있기 때문이다 |
| **WebSocket 재연결** | 장중에도 서버가 세션을 끊을 수 있다(실측 14:00, 1초 만에 자동 재연결). 재연결 후 **보유 종목부터** 순서대로 REST 현재가로 공백 구간을 보정한다. 장 운영시간 밖에는 보정을 생략한다 |
| **시장가 슬리피지** | 익절 트리거 가격과 실제 체결가는 다르다(실측: 트리거 2,594원 → 체결 2,580원, **-0.56%**). 거래량이 얇은 종목일수록 커지므로 +3% 익절의 실질 수익은 그보다 낮게 잡는 것이 현실적이다 |
| **권장 운용 시간** | 정규장 09:00~15:30. **08:40~08:50** 프로그램 시작(연결·복원·잔고 대조) → **08:55 전후** 감시 시작 → **15:30 이후** 감시 중지. 15:20~15:30 종가 동시호가에서도 시장가 주문은 정상 처리된다 |
| **예수금 기준** | 프로그램은 정산이 끝난 뒤 남는 **D+2 추정예수금**을 기준으로 삼는다. 증권사 앱의 '인출 가능금'보다 작을 수 있는데, 오늘 매수한 대금이 2영업일 뒤에 빠져나가기 때문이다(가장 보수적이고 안전한 기준) |
| **금액 용어 구분** | 영웅문에 비슷한 이름이 많아 혼동하기 쉽다. **예수금 잔액**은 계좌 현금 총액, **인출 가능금**은 은행으로 뺄 수 있는 돈, **주문가능금액**은 지금 더 매수할 수 있는 돈이다. 프로그램이 표시·판정에 쓰는 값은 **주문가능금액**이며 화면에도 그 이름으로 적는다. **대용금**은 보유 주식을 담보로 환산한 값이라 매수 여력과 무관하고, 추정자산에 더하면 이중 계상이 된다 |
| **주문가능금액 필드** | 예수금 응답에는 성격이 다른 금액이 여럿 있다(실측 2026-07-28): `ord_alow_amt` 는 **주문가능현금**(119,391)이라 당일 매도대금 재사용분이 빠져 있고, `100stk_ord_alow_amt` 가 **증거금 100% 종목 주문가능금액**(1,399,983 = 현금 + 재사용분)이다. 미수를 쓰지 않는 전략이므로 후자가 맞는 상한이며, 전자를 쓰면 자금이 있는데도 진입이 막힌다 |
| **계좌 유형별 필드** | 예수금이 실리는 응답 필드는 계좌 유형마다 다르다. 해외주식 원화주문(통합증거금) 계좌는 일반 현금 필드가 0 으로 오고 대용 설정 필드에 금액이 잡힌다(실측). 후보 필드를 순서대로 탐색해 처리하며, 한 번 성공한 조합은 기억해 호출 수를 줄인다 |
| **개장 직후 슬리피지** | 09:00~09:05 는 호가가 얇아 시장가가 크게 밀린다(실측 2026-08-13: 판정 9,300 → 체결 9,750, **+4.84%**. 같은 날 나머지 7건 평균은 +0.42%). 체결통보도 2분 넘게 늦을 수 있다(2026-08-11 125초, 08-13 134초). 판정과 체결 사이의 공백을 줄이려고 20초 뒤부터 REST(ka10076)로 체결을 직접 확인한다 |
| **'매매만' 은 잡음을 끄는 것이지 사고를 숨기는 게 아니다** | 예전 알림 필터는 종류와 무관하게 시스템 로그를 전부 막아, **키움 연결 실패·자동 시작 실패·휴장 안내**까지 폰으로 가지 않았다(2026-08-17 확인, 해당 로그 15건). 경고·에러는 수준과 무관하게 보낸다 — 일부러 끈 '끔' 만 예외다 |
| **하루 한 번 알림은 메모리에 표시한다** | DB 에 남기면 재시작해도 다시 알리지 않아, 나중에 켠 창에서는 왜 감시가 안 도는지 알 수 없다(2026-08-17 실측: 휴장 안내가 그날 첫 실행에서만 남았다) |
| **색은 값이 아니라 뜻으로 관리** | 색을 파일마다 적어 두면 모드를 바꿀 때 전부 찾아 고쳐야 한다. `theme.py` 에 '이익·손실·주의·비활성' 같은 **뜻**으로 두고 모드마다 값을 갈아끼운다. 값은 **명암비 4.5 이상**(WCAG 본문 기준)을 지키도록 골랐고 테스트로 고정했다 — 예전 색은 다크에서 빨강 2.7·파랑 2.6, **라이트에서도 주황 1.7·회색 2.4** 로 이미 잘 안 보였다 |
| **입력 감지는 KeyRelease 가 아니라 변수 변경** | 한글은 조합이 끝나야 위젯에 글자가 들어오는데, 그 확정 시점이 키를 떼는 순간이 아니다(다음 글자 입력·포커스 이동 등). KeyRelease 에만 걸면 '서산' 을 쳐도 '서' 로만 걸러지고 다른 곳을 클릭해야 반영된다(2026-08-15 실측). StringVar 변경을 보면 어떤 경로로 들어오든 잡힌다. **조합 중인 마지막 글자는 OS 가 별도 창에 그려 Tk 가 읽을 수 없다** — 다만 부분 일치 검색이라 '서' 만으로도 '서산' 이 이미 보인다 |
| **휴장일은 KRX 목록이 유일한 답** | 공휴일 API 로는 부족하다 — **근로자의날(5/1)·연말휴장일(12/31)은 법정공휴일이 아닌데 증시는 쉰다**. 반대로 임시공휴일처럼 규칙으로 못 만드는 날도 있다. KRX 공지(보통 12월 초)를 받아 `holidays.csv` 에 **덧붙인다**(지난 해를 지우면 과거 날짜의 휴장 사유를 알 수 없다). 파일은 `data/` 가 아니라 **루트에 두고 git 으로 관리**한다 — `data/` 는 .gitignore 라 다른 PC 에서 사라진다 |
| **종목 검색은 숨김 방식** | 100종목이 넘어 필요하지만, **살아 있는 감시 화면을 가리는** 기능이라 규칙을 좁게 잡았다. 평소에는 검색줄이 없고 Ctrl+F 로만 뜬다. **필터가 걸려 있으면 검색줄은 사라지지 않는다** — 줄이 없는데 종목만 줄어 있으면 왜 안 보이는지 알 수 없기 때문이다(검색줄을 닫는 것 = 필터를 푸는 것). 숨긴 행도 값은 계속 갱신되고, 숨긴 종목은 Tk 가 선택 자체를 막아 주문이 나갈 수 없다 |
| **조용히 멈추는 것이 가장 위험하다** | 매매가 멈추는 길은 대개 오류창이 아니라 **침묵**이다. 2026-08-19 점검에서 다섯 군데를 막았다 — ① 코어 루프에 방어가 없어 예외 하나로 스레드가 통째로 죽었다(화면은 멀쩡, 데몬 스레드라 아무도 모름) ② 그 죽음을 알릴 길이 없었다 → 이벤트 큐로 화면에 남긴다 ③ `requests` 의 Timeout·ConnectionError 가 `BrokerError` 로 변환되지 않아 **주문 중 타임아웃이 WebSocket 을 끊고**(재연결로 위장) 실패 표시도 안 남아 다음 틱에 같은 주문을 다시 낼 수 있었다 ④ `create_task` 로 띄운 알림·차트 전송의 실패가 조용히 사라졌다 ⑤ 우리 판정 코드의 예외가 수신 루프까지 올라가 무한 재연결이 될 수 있었다. **격리하되 반드시 눈에 보이게 남긴다**(같은 원인은 한 번만) |
| **연결됐다고 살아 있는 건 아니다** | 2026-08-18: 09:33 프로토콜 오류로 WebSocket 이 끊겼다가 09:34 **재연결에 성공**했는데, 그 뒤 15:30 까지 틱이 한 건도 오지 않았다. 프로그램은 6시간 내내 '연결됨' 이었고 그날 1선을 이탈한 **11종목이 통째로 진입하지 못했다**. 서버가 protocol ping 에는 답하면서 시세만 안 보내면 라이브러리 keepalive(ping_interval=20)로는 잡히지 않고 `async for` 가 영원히 기다린다. 그래서 **틱이 오는지를 직접 본다** — 장중에 90초 침묵이면 연결을 다시 맺고 경고를 보낸다(118종목이면 몇 초에 한 번은 온다) |
| **손익은 '그날' 과 '이 매매' 를 나눠 센다** | 이월이 포지션을 통째로 복사하던 시절, 어제 번 돈이 오늘 것으로 다시 계산됐다(2026-08-18 씨앤씨인터내셔널: 평단 그대로 팔아 오늘 0원인데 +707원으로 보고, 증권사 대조가 잡아냄). 한 값이 **"오늘 얼마 벌었나"**(UI 상단·일일 요약·대조)와 **"이 매매로 얼마 벌었나"**(매매일지·종료 알림) 둘 다에 답하려던 것이 원인이다. 이제 날짜별 행에는 **그날 것만** 담고, 매매 전체는 `cycle_totals` 로 **합산**해서 구한다 |
| **UI 고장 격리** | 화면 갱신 중 예외가 나면 폴링 루프가 다시 예약되지 않아 **매매는 계속되는데 화면만 멈춘다**(실측 2026-08-13: PositionsView.set_blocked 누락). 낡은 값을 보며 판단하게 되는 가장 위험한 고장 방식이라, 이벤트 하나의 실패가 루프를 끊지 못하게 막고 실패는 로그와 터미널에 남긴다. `test_ui_dispatch.py` 가 코어의 이벤트 목록을 코드에서 뽑아 전부 처리해 본다 |
| **모드별 기록 분리** | 모의와 실전은 DB 파일이 분리되어 있어 기록이 섞이지 않는다. 다만 **같은 날 두 모드를 번갈아 운용하면 계좌 잔고와 프로그램 상태가 어긋날 수 있으므로** 하루에 한 모드만 사용한다 |

**차트 데이터 실측 메모** (2026-07-27)

- 지수(KOSPI)는 소수 2자리를 정수로 준다 → ÷100 보정 (669062 = 6,690.62)
- 거래대금은 TR 단위가 다를 수 있어 `종가×거래량` 대조로 10ⁿ 배율을 자동 보정한다
  (실측 대조: 영웅문 375,741백만 = 차트 3,757억 — 일치)
- 시가 필드는 이름이 비슷한 다른 값과 섞일 수 있어 **저가~고가 범위 검사**로 걸러낸다
- **차트는 통합(KRX+NXT) 코드로 조회한다** — 종목코드에 `_AL` 을 붙이면 영웅문
  '통합키움차트' 와 값이 정확히 일치한다(실측: 5일 × 시/고/저/종/거래량 전부 일치).
  접미사 없이 조회하면 KRX 단독이라 시가가 0/7 일치, 거래량이 2.4배 차이 났다.
  NXT 미상장 종목을 대비해 통합 코드 결과가 비면 원래 코드로 자동 폴백한다
- **분봉(ka10080)은 정규장 범위만 돌려준다.** 통합 코드(`_AL`)를 써도 마지막 봉이 항상
  15:30 이고, 요청 파라미터에 시간외를 포함하는 옵션이 없다(공식 문서 확인, 2026-08-11).
  일봉은 통합이라 NXT 거래가 반영되지만 분봉은 아니다. 이 때문에 20:05 시간외 리뷰는
  대상이 늘 0종목이었고, 기능 자체를 제거했다
- **매매 판정(WebSocket 시세)과 주문은 KRX 기준 그대로**다 — 주문을 내는 거래소와
  판정 근거를 일치시키기 위한 의도된 분리다

### exe 로 배포할 때 확인할 것

지금은 VS Code(`uv run main.py`)로 운용하지만, 나중에 PyInstaller 등으로 실행파일을 만들 때
아래를 함께 챙겨야 자동 스케줄이 동일하게 동작한다.

1. **작업 디렉터리** — `config.toml` 과 `data/` 를 상대 경로로 읽는다. 작업 스케줄러의
   "시작 위치"를 exe 가 있는 폴더로 지정하거나, 실행 시 작업 디렉터리를 고정해야 한다.
2. **숨은 의존성** — `tkcalendar`, `babel` 등 동적 import 되는 패키지는 자동 수집되지 않을 수 있어
   `--hidden-import` 또는 `--collect-all` 지정이 필요하다.
3. **아이콘·데이터 파일** — `assets/` 는 코드가 아니므로 `--add-data` 로 함께 넣고, 경로를
   실행 환경에 맞게 해석해야 한다(PyInstaller 는 임시 폴더에 풀어 놓는다).
4. **콘솔 창** — `--noconsole` 로 만들면 예외 메시지가 화면에 안 보인다. 로그가 DB 에 남지만,
   초기에는 콘솔을 켜둔 채로 며칠 운용해 보는 편이 안전하다.
5. **중복 실행 방지** — 포트 점유 방식이라 exe 에서도 그대로 동작한다. 다만 방화벽이 로컬
   포트 바인딩을 막지 않는지 첫 실행 때 확인한다.
6. **작업 스케줄러 재등록** — 프로그램 항목을 `start.bat` 에서 exe 경로로 바꾸고, 시작 위치는
   그대로 유지한다.
7. **matplotlib 포함** — 복기 차트용 matplotlib 이 exe 용량을 크게 늘린다(수십 MB). Agg 백엔드만
   쓰므로 `--exclude-module` 로 불필요한 백엔드(tk/qt 연동 등)를 제외하면 줄일 수 있다.
   차트 한글 폰트는 OS 폰트를 쓰므로 별도 포함이 필요 없다.
